# French coverage and French-first places (S-116, Loi 96 readiness)

Northline is bilingual (en, fr-CA) everywhere. Where a place's language law puts French first — Québec's Charter of
the French Language as amended by Bill 96 is the first such case — the product behaves French-first there. Which
places those are is **region configuration**, never code (DECISIONS "Region-neutral by design").

> **Not legal advice.** No certified translator has reviewed any of Northline's French, and counsel has not confirmed
> this reading of Loi 96 (counsel question D1, [compliance/legal/counsel-questions.md](../compliance/legal/counsel-questions.md)).
> Both are launch blockers for a French-first place: `make i18n-check STRICT=1` fails until they are done.

## 1. The gate: `make i18n-check`

`scripts/i18n/coverage.mjs` finds every customer-facing string without French; `scripts/i18n/coverage.test.mjs` tests
the scanner and runs it on the repository. Node only (the TypeScript compiler comes from `web/node_modules`).

```
make i18n-check            # tests + report; fails on any gap except the known ones
make i18n-check STRICT=1   # also fails on the known gaps: run before opening any French-first place
node scripts/i18n/coverage.mjs --json   # the same, as JSON
```

| surface | what is checked |
|---|---|
| `web-bundles` | every `defineMessages` / `messagesFor` catalogue and inline `{ en, fr }` pair in the consumer web, Studio, console, docs site and shared packages: the same keys, no empty French, no French equal to the English unless it has no words to translate (brands, units, placeholders, identifiers) or is in `sameInFrench`; the docs site's `<Translate>` ids against `i18n/fr/code.json`; every public guide has its French page |
| `web-jsx` | text written straight into JSX (text nodes; `placeholder`, `title`, `aria-label`, `alt`, `label`) outside a catalogue |
| `mobile` | the consumer and courier apps' `en` / `fr-CA` catalogues (same checks), their iOS/Android system strings (`locales/*.json`) and their JSX text |
| `server` | the validation catalogue (`docs/spec/validation-messages.fr-CA.tsv`: French present, status `shipped`/`new`/`review`), every `new NotFound("…")` resource (the 404 detail) and every HTTP status title (the ProblemDetail title), the e-mail bundles (`messages.properties` vs `messages_fr.properties`) and templates (no literal words), the SMS / push wordings (`Notices`, `PersonalNotices` EN/FR maps) |
| `catalogue` | every category of `db/seed/categories.json` has a French name (`catalogue.category_labels`, V111 + V316) |
| `store` | every en-CA App Store field and Play listing file has its fr-CA counterpart |
| `legal` | every legal text of the registry (`web/packages/legal/registry.json`, S-106) has a French version — Terms and Privacy Policy are **known gaps** |
| `review` | every row of `docs/i18n/translation-review.csv` still matches its source; rows awaiting a translator are a known gap |

**A finding** names the file and key. Fix it by writing the French in the catalogue (never by copying the English);
add the row to `docs/i18n/translation-review.csv` (`key,source,french,status` with `needs translator review`). A value
that is genuinely the same in French ("Total", "Menu", a language's own name) goes in `scripts/i18n/allowlist.json`
`sameInFrench`; a sample value that isn't language (a GST number's shape) in `jsx` for that file.

**Known gaps** (`allowlist.json` `legalKnownGaps`, the review file) are printed on every run and fail only with
`STRICT=1`. Server messages that the S-40 Java test (`ValidationMessageCatalogueTests`) also guards fail the server
build too.

## 2. French-first places (region configuration)

`region.regions` (V315): `french_first` (boolean) and `french_listings` (`off` | `warn` | `require`) on province rows; on
a market row `NULL` means "the province's". V315 seeded them from each province's first official language
(`region.regions.languages`, V117). `REGION_FRENCH_FIRST` (api) adds places by configuration: province codes or market
ids, comma-separated; those are French-first with `require`. **A French-first place always requires French listings**
(owner decision 2026-10-04): the api reads `warn` or `off` on a French-first row as `require`; `warn` is for places
that aren't French-first (a province that wants French encouraged, not required).

```sql
-- a market that is French-first in a province that isn't (or the reverse: false)
UPDATE region.regions SET french_first = true, french_listings = 'require' WHERE id = '<market id>';
-- French encouraged (the Studio warns) where French isn't first
UPDATE region.regions SET french_listings = 'warn' WHERE id = '<market id>';
-- back to the province's rule
UPDATE region.regions SET french_first = NULL, french_listings = NULL WHERE id = '<market id>';
```

Rows are picked up within `REGION_CACHE_TTL`. Check `GET /api/v1/geo/regions` (`frenchFirst`, `frenchListings` on
every province and market) and, for a business, `GET /api/v1/merchants/{id}` → `region.frenchFirst`.

What a French-first place changes:

| where | behaviour |
|---|---|
| consumer web | French when the visitor hasn't chosen (no `nl.locale` cookie, no `?lang=`) and their delivery location's place is French-first; any visitor whose browser prefers French (q-weights) gets French too |
| Terms and Privacy Policy | presented in French first at registration; English only on an express request, recorded with the acceptance (`identity.users.terms_language`, `terms_english_requested_at`, V319). **The French texts don't exist yet** — the form says so, and the gate's strict run fails |
| Studio | a business there opens the Studio in French unless the person chose a language with the switch |
| listings | `warn`: the editor's French panel says the French name and description are missing; `require`: and submit / publish answer 422 `french` until both are written (`catalogue.listing_texts`, V317). Customers reading French see them |
| receipts | Stripe's receipt e-mails in French (the Customer's `preferred_locales`, V318) — French only, also for an English-speaking customer: Stripe makes no bilingual receipt, and the owner accepted French-only receipts for French-first merchants (2026-10-04); Northline's own e-mails, SMS, push and PDF statements follow the person's language as before, formatted fr-CA |
| consumer app, courier app | French when the person (courier) hasn't picked a language and their place (courier's market) is French-first |
| help centre, support | already bilingual (help articles and macros en + fr since V072/V214); cases keep the requester's language |

Formatting is `Intl` / `java.text` with `fr-CA` everywhere (web `formatMoney`/`formatDate`, mobile-kit, `EmailFormat`,
the PDF statements): `1 234,56 $`, `2 octobre 2026`, `9 h 00`.

## 3. Before opening a French-first place

1. Counsel answers D1 (and D2–D3) in `docs/compliance/legal/counsel-questions.md`; French Terms and Privacy Policy
   are published in `web/packages/legal/pages/*.fr-CA.html`, recorded in the registry, and added to `FRENCH_LEGAL`
   (`web/apps/consumer/src/lib/legal.ts`).
2. A certified translator reviews `docs/i18n/translation-review.csv`, then every catalogue's French (the validation
   TSV's `new` and `review` lines first); mark rows `reviewed`.
3. `make i18n-check STRICT=1` passes.
4. The place's region rows say `french_first = true` and the wanted `french_listings`.
