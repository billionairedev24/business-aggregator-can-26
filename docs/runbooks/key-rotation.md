# Key rotation runbook (S-7, S-115)

Every key and secret Northline holds, how to rotate it on a schedule and what to do when one leaks. One section per
key: symptoms, impact, decision tree, exact commands, verification, rollback and comms, then what was exercised. The
secret inventory (names per cloud, which app reads what) is [secrets.md](secrets.md); this page is the procedures.

| key / secret | where it lives | overlap during a rotation | rotate | § |
|---|---|---|---|---|
| auth token signing keys (JWKS) | `KMS_PROVIDER`: a local JWK set file, or AWS KMS / Cloud KMS / Key Vault | yes: publish ahead, keep the retiring key published 1 h | yearly, and when someone with access leaves | [1](#1-auth-signing-keys-jwks-rollover-with-overlap) |
| KMS data keys (envelope encryption of stored tokens) | `KMS_ENCRYPTION_KEY_ID` (cloud) / `KMS_LOCAL_KEY` | yes: old key (version) unwraps until the re-wrap job finished | cloud: yearly (automatic key rotation); local: when it leaks | [2](#2-kms-data-keys-and-envelope-re-wrap) |
| merchants' webhook signing secrets (`whsec_…` per endpoint) | `developer.webhook_endpoints.secret_enc`, sealed with `WEBHOOK_SECRET_KEY` | yes: both secrets sign for 0–168 h (default 24 h) | the business decides (Studio); support helps | [3](#3-merchants-webhook-signing-secrets) |
| Stripe API keys, Stripe webhook secrets | secrets manager: `stripe-secret-key`, `stripe-webhook-secret`, `stripe-connect-webhook-secret` | yes: Stripe keeps the old key / signs with both secrets for the time you choose | yearly; at once when leaked | [4](#4-stripe-api-keys-and-webhook-secrets) |
| DB password, Kafka credentials, push keys (APNs `.p8`, FCM), OpenRouter key, on-call export token | secrets manager (generated by Terraform or set by the operator) | depends on the provider (table in § 5) | yearly; at once when leaked | [5](#5-database-kafka-push-openrouter-on-call-export) |
| the mechanics for every secret above: put a new version, refresh the Kubernetes Secret, restart | External Secrets on AWS / Google Cloud / Azure | — | — | [6](#6-external-secrets-commands-per-cloud) |

**General decision tree** (every section refines it):

```
Is the key leaked, or possibly leaked (a commit, a log, a laptop lost, a leaver with access)?
├─ yes → EMERGENCY: no overlap. Revoke the old value first if the service allows a short outage, else rotate with the
│        shortest overlap; then look for misuse in the provider's logs. Tell security; incident note.
└─ no  → PLANNED: use the overlap, in a quiet hour, one environment at a time (dev → staging → prod), and verify
         between each step. Nobody needs to be told unless a step signs people out (none here does).
```

**Comms for every planned rotation:** a line in the ops channel before (what, which environment, expected impact:
none) and after (done, verified). For an emergency: security lead + incident note with the timeline.

## 1. Auth signing keys (JWKS rollover with overlap)

**Symptoms that call for it.** The yearly schedule; someone with KMS or key-file access leaves; a key or the JWK set
file may have been copied (a backup in the wrong place, a debug dump). Signs of a *bad* rotation: the api answers 401
`invalid_token` right after a switch; `/oauth2/jwks` lacks the kid tokens carry.

**Impact.** A planned rotation: none (publish → switch → retire, each a rolling deploy that only adds before it
switches). An emergency rotation: access tokens signed by the old key fail until the BFFs refresh them (≤ 10 min);
refresh tokens and sessions are opaque, so nobody is signed out.

**Decide:** local provider (dev, laptops) → *Rotating — local provider*; cloud → *Rotating — cloud providers*;
compromised → *Compromised key (emergency)*. With Terraform managing the key → [infrastructure.md § Signing key
rotation](infrastructure.md#signing-key-rotation-with-terraform-s-7).

**Verify after every step:** `curl -s https://auth.<domain>/oauth2/jwks | jq '[.keys[].kid]'` lists the expected kids;
the auth log line `Signing keys: provider=… active=<kid> … published=[…]`; a fresh sign-in's access token header
(`echo <token> | cut -d. -f1 | base64 -d`) carries the new kid after the switch; the api accepts it (any Studio page
loads).

**Rollback.** Before the retire step, set `KMS_KEY_ID` back to the old key (it is still published) and deploy — tokens
from both keys verify. After the retire step, the old key is gone from the JWK set: publish it again first
(`KMS_PUBLISHED_KEY_IDS=<old>`), wait 5 min, then switch.

**Comms.** Planned: none beyond the ops channel. Emergency: as above; if sessions were revoked too, support expects
"I was signed out" tickets.

### How it works

northline-auth signs every token it issues — access tokens, ID tokens and the finance step-up proofs — with one ES256
(EC P-256) key. The **active** key signs. `https://auth.<domain>/oauth2/jwks` publishes the active key, a **next** key
waiting to take over, and **retiring** keys that are kept only so the tokens they signed still verify. The `kid` of
every token is the RFC 7638 thumbprint of its key, so every replica and every environment names a key the same way.

Who reads the JWK set: the api (resource server via `AUTH_ISSUER` discovery, and `JwtStepUpVerifier` for payouts), the
studio-bff (`AUTH_INTERNAL_URL/oauth2/jwks`, ID tokens) and northline-auth itself (userinfo). They cache it for up to
5 minutes and fetch it again when a token has a `kid` they don't know. Refresh tokens are opaque (stored in
`auth.oauth2_authorization`), so a rotation never signs anyone out.

Code: `server/auth/src/main/java/ca/northline/auth/signing` (`SigningKeys` port, `LocalFileSigningKeys`,
`RemoteSigningKeys` + `AwsKmsKeyService` / `GcpKmsKeyService` / `AzureKeyVaultKeyService`, `KeyStoreJwtEncoder`).

### Choosing the provider

| `KMS_PROVIDER` | where the private key is | who signs | allowed under | `KMS_KEY_ID` |
|---|---|---|---|---|
| `local` (default) | JWK set file `signing-keys.jwks.json` (mode 600) in `SIGNING_KEYS_DIR` (default `~/.northline/auth-signing-keys`), created on first start | northline-auth | `local`, `test`, `dev` (with a volume shared by the replicas) | — |
| `aws` | AWS KMS, key spec `ECC_NIST_P256`, usage `SIGN_VERIFY` | KMS (`kms:Sign`, `ECDSA_SHA_256` on the digest) | every profile | key ARN (or alias ARN — prefer the key ARN, see rotation) |
| `gcp` | Cloud KMS, algorithm `EC_SIGN_P256_SHA256`, purpose `ASYMMETRIC_SIGN` (protection level HSM recommended) | Cloud KMS (`asymmetricSign`) | every profile | the key **version** resource name `projects/…/locations/…/keyRings/…/cryptoKeys/…/cryptoKeyVersions/N` |
| `azure` | Azure Key Vault (or Managed HSM), key type `EC-HSM` (Premium vault) or `EC`, curve `P-256` | Key Vault (`sign`, `ES256`) | every profile | the key identifier URL **with** its version `https://<vault>.vault.azure.net/keys/<name>/<version>` |

- Under `staging` and `prod` the app refuses to start without `KMS_PROVIDER` and `KMS_KEY_ID`
  (S-1 required-environment check: purposes `signing-provider` and `signing-key`) and refuses `KMS_PROVIDER=local`.
  `dev` only requires `KMS_PROVIDER`.
- Cloud providers fetch the public keys of `KMS_KEY_ID` and `KMS_PUBLISHED_KEY_IDS` at start-up: a wrong id, a key of
  the wrong type or a missing permission stops the start-up with the reason, never the first sign-in.
- Credentials are never variables of ours: AWS SDK default chain (IRSA / EKS Pod Identity), Google Application
  Default Credentials (Workload Identity), Azure `DefaultAzureCredential` (AKS workload identity).
- Only the chosen provider's client is created; the three SDKs ship in the jar either way.

| variable | default | meaning |
|---|---|---|
| `KMS_PROVIDER` | `local` | `local` · `aws` · `gcp` · `azure` |
| `KMS_KEY_ID` | — | the key that signs (cloud providers) |
| `KMS_PUBLISHED_KEY_IDS` | empty | comma-separated keys published without signing: the next key before a switch, the previous one after it |
| `KMS_REGION` | SDK default (`AWS_REGION`) | AWS only |
| `KMS_ENDPOINT` | provider endpoint | AWS only (LocalStack, VPC endpoint URL) |
| `SIGNING_KEYS_DIR` | `~/.northline/auth-signing-keys` | `local` only: directory of the key file; every replica must mount the same one |
| `SIGNING_KEYS_ROTATE_EVERY` | empty (off) | `local` only: rotate automatically when the newest key is this old, e.g. `90d` (checked hourly under the file lock, so N replicas rotate once) |

#### Creating the key (until Terraform does it — S-2)

**With Terraform (S-2):** `infra/terraform/envs/<cloud>/<env>` creates the `signing` key (HSM-backed in prod on
Google Cloud and Azure), grants only the `northline-auth` workload identity sign + get-public-key on it, and writes
`KMS_PROVIDER`, `KMS_KEY_ID` (AWS key ARN · Google Cloud key version `…/cryptoKeyVersions/1` · Azure versioned key URL)
and `KMS_PUBLISHED_KEY_IDS` into `config_env`; rotations set them through `signing_key_ids`
([infrastructure.md § 4](infrastructure.md#signing-key-rotation-with-terraform-s-7)). The commands below are for an
environment Terraform doesn't manage, and for the new key of an AWS rotation.

Always in the environment's Canadian region. The workload identity of northline-auth needs **sign** and **read the
public key** on this key only.

```sh
# AWS — policy: kms:Sign, kms:GetPublicKey on the key ARN
aws kms create-key --region ca-central-1 --key-spec ECC_NIST_P256 --key-usage SIGN_VERIFY \
  --description "northline-auth token signing (prod)" --query KeyMetadata.Arn --output text

# Google Cloud — role roles/cloudkms.signerVerifier (+ roles/cloudkms.publicKeyViewer) on the key
gcloud kms keyrings create northline-auth --location northamerica-northeast1
gcloud kms keys create token-signing --keyring northline-auth --location northamerica-northeast1 \
  --purpose asymmetric-signing --default-algorithm ec-sign-p256-sha256 --protection-level hsm
gcloud kms keys versions list --key token-signing --keyring northline-auth \
  --location northamerica-northeast1 --format='value(name)'            # → KMS_KEY_ID

# Azure — role "Key Vault Crypto User" on the key (or vault)
az keyvault key create --vault-name <vault> --name token-signing --kty EC-HSM --curve P-256 --ops sign verify \
  --query key.kid --output tsv                                         # → KMS_KEY_ID (versioned URL)
```

Check after a deploy: `curl -s https://auth.<domain>/oauth2/jwks | jq '.keys[].kid'` lists the expected kids, and the
auth log has `Signing keys: provider=… active=<kid> (…) published=[…]`.

### Rotating — local provider

The command edits the key file; running servers notice the change (file time, re-read at the latest every 30 s). No
restart. From `server/`:

```sh
./gradlew :auth:signingKeys --args='status'
./gradlew :auth:signingKeys --args='rotate'        # new key published now, signs 10 min later; old key kept 1 h more
# other directory or timings:
./gradlew :auth:signingKeys --args='rotate --dir=/var/lib/northline/keys --publish-ahead=10m --retire-after=1h'
# from a built jar (e.g. in a dev pod that mounts SIGNING_KEYS_DIR):
java -cp northline-auth.jar -Dloader.main=ca.northline.auth.signing.SigningKeysCommand \
  org.springframework.boot.loader.launch.PropertiesLauncher rotate
```

What `rotate` does: adds a key with `nbf = now + publish-ahead` (published at once, signing from `nbf`) and gives the
keys signing until then `exp = nbf + retire-after`. Keys past `exp` disappear from the JWK set and from the file at the
next rotation. `publish-ahead` must exceed the JWK set caches (5 min); `retire-after` must exceed the longest token
lifetime (ID tokens 30 min, access tokens 10 min, step-up proofs 5 min). Or set `SIGNING_KEYS_ROTATE_EVERY=90d`.

Losing the file only costs the tokens in flight: a new key is generated, access tokens already issued (≤ 10 min)
fail at the api until the BFF refreshes them, while refresh tokens and sessions survive (they are not signed).

### Rotating — cloud providers

A new key (AWS) or key version (GCP, Azure) plus two configuration changes. Each step is a normal rolling deploy of
northline-auth; old and new replicas stay compatible at every step because each step only *adds* to what is published
before anything signs with it.

1. **Create** the new key / version (commands above; GCP: `gcloud kms keys versions create --key token-signing …`;
   Azure: `az keyvault key rotate` or `key create` again → new versioned URL). Grant the same permissions.
2. **Publish it**: `KMS_PUBLISHED_KEY_IDS=<new id>` (keep `KMS_KEY_ID=<old id>`). Deploy. Check the JWK set lists both
   kids. **Wait at least 5 minutes** (JWK set caches).
3. **Switch**: `KMS_KEY_ID=<new id>`, `KMS_PUBLISHED_KEY_IDS=<old id>`. Deploy. New tokens carry the new kid; tokens
   signed by the old key still verify.
4. **Retire**: after at least 1 hour (longest token lifetime + slack), `KMS_PUBLISHED_KEY_IDS=` (empty). Deploy.
   Then disable the old key/version in the KMS (AWS `disable-key` + `schedule-key-deletion` after a grace period;
   GCP `versions disable`/`destroy`; Azure disable the version).

Rotate at least yearly and whenever someone who could use the key leaves. Don't use AWS aliases as `KMS_KEY_ID`
while rotating: re-pointing an alias switches every replica at a random moment instead of step 3.

### Compromised key (emergency)

Tokens signed by the compromised key must stop being accepted at once. Refresh tokens and sessions are not signed with
it, so people stay signed in; calls with an old access token fail until the BFF refreshes it.

- **local**: `./gradlew :auth:signingKeys --args='rotate --immediately'`, then
  `./gradlew :auth:signingKeys --args='retire <compromised kid>'`.
  A planned rotation still pending (a **NEXT** key in `status`) survives `rotate --immediately` and would take over
  at its time: if it was created before the compromise, `retire` it too (found in the S-115 drill).
- **cloud**: create a new key, set `KMS_KEY_ID=<new>` and `KMS_PUBLISHED_KEY_IDS=` (empty) in one deploy, then disable
  the compromised key in the KMS. Until JWK set caches expire (≤ 5 min) the api may still accept old tokens: restart the
  api and the bff to drop their caches at once.
- If the sessions themselves may be compromised too, revoke them: delete the rows of `auth.oauth2_authorization`
  (refresh tokens) and flush the `nl:auth:*` and `nl:studio-bff:*` sessions in Valkey (everyone signs in again).

### Troubleshooting

| symptom | cause / fix |
|---|---|
| `KMS_PROVIDER=local is not allowed under staging/prod` | set `KMS_PROVIDER` to `aws`, `gcp` or `azure` and `KMS_KEY_ID` |
| `APPLICATION FAILED TO START … signing-provider: KMS_PROVIDER` / `signing-key: KMS_KEY_ID` | the variables are missing (S-1 check) |
| `KMS key … is RSA_2048, not ECC_NIST_P256` (or the GCP/Azure equivalent) | wrong key type: create an EC P-256 signing key |
| AccessDenied / PERMISSION_DENIED / 403 at start-up | the workload identity lacks sign / get-public-key on that key |
| api answers 401 `invalid_token` right after a switch | step 2 was skipped or shorter than 5 min: publish first, then switch |
| `No usable signing key in …/signing-keys.jwks.json` | every key in the file has expired (clock jump, manual edit): `rotate --immediately` |

## 2. KMS data keys and envelope re-wrap

The api keeps a few secrets it must use later — calendar refresh tokens (S-32), commerce and POS credentials
(S-35, S-36), customers' access notes for bookings (S-55) — **envelope-encrypted** (`SecretSealer`): each value has
its own AES-256-GCM data key, and the data key is wrapped by the key service (`KMS_PROVIDER`, key
`KMS_ENCRYPTION_KEY_ID`, or `KMS_LOCAL_KEY`). Each row stores the reference of the key that wrapped it (`token_ref` /
`key_ref`): the local key's fingerprint, the AWS key ARN, the Cloud KMS key **version** (since S-115; older rows the
key name), or the Key Vault key version URL.

**The re-wrap job (S-115).** Every `KMS_REWRAP_EVERY` (1 h, first run 2 min after start) each api replica re-wraps,
200 rows per table at a time, every value whose reference isn't the current one: unwrap with the old key, wrap with
the current key, store the new wrapped data key. The ciphertext never changes, the plaintext never leaves memory.
Tables come from the modules (`SealedColumn` beans): `availability.calendar_links`, `catalogue.integrations`,
`food.pos_connections`, `booking.access_notes`. Metric `northline_crypto_rewrapped_total{table,outcome}`; log
`Key re-wrap: <table> — N re-wrapped with <ref>, M failed`. Slot holds in Valkey (sealed checkout drafts, ≤ 15 min)
expire on their own.

**Symptoms that call for it.** Yearly; the `tokens` key (or `KMS_LOCAL_KEY`) may have leaked; someone with decrypt on it
left. A *broken* rotation shows as calendars dropping to "reconnect", commerce/POS syncs failing with
`Decryption failed` or `Sealed with another key`, and `Key re-wrap: … failed` lines.

**Impact.** Planned: none — old values stay readable until re-wrapped. If the old key is disabled before the job
finished: those calendar / commerce / POS connections ask their owner to reconnect, and the access notes of those
bookings can't be shown to the provider (the booking itself is unaffected).

**Decide:**

```
which provider?
├─ AWS: automatic key rotation (yearly, same ARN) → nothing to do: KMS keeps the old key material and decrypts with it;
│        no re-wrap needed. A NEW key (leak, policy): create it, grant the api encrypt+decrypt on BOTH keys, set
│        KMS_ENCRYPTION_KEY_ID=<new ARN>, deploy; the job re-wraps; then remove decrypt on the old one and disable it
├─ Google Cloud: new primary version (automatic rotation period or by hand) → the job re-wraps values of older
│        versions (their ref names the version); then disable / destroy the old version
├─ Azure: new key version (`az keyvault key rotate` or a rotation policy) → set KMS_ENCRYPTION_KEY_ID to the new
│        versioned URL, deploy; the job re-wraps; then disable the old version
└─ local (dev, laptops, the kind rehearsal): KMS_LOCAL_KEY=<new>, KMS_LOCAL_PREVIOUS_KEYS=<old>, restart; the job
         re-wraps; then empty KMS_LOCAL_PREVIOUS_KEYS and restart
leaked? → same steps, but don't wait for the yearly window; after the re-wrap, disable the old key at once
```

**Commands.**

```sh
# AWS — automatic rotation (nothing else to do afterwards), or a new key for a leak
aws kms enable-key-rotation --key-id <tokens key ARN> --rotation-period-in-days 365
aws kms create-key --region <region> --description "northline api tokens (<env>)" --query KeyMetadata.Arn --output text
#   grant the api role kms:Encrypt + kms:Decrypt on the new ARN (Terraform: module kms, key "tokens"), keep Decrypt on the old

# Google Cloud — a new primary version now (or set a rotation period: --rotation-period=365d --next-rotation-time=…)
gcloud kms keys versions create --key tokens --keyring northline-<env> --location <region> --primary
gcloud kms keys versions list --key tokens --keyring northline-<env> --location <region>

# Azure — a new version, then point the api at it
az keyvault key rotate --vault-name <nl-<env>-kms-…> --name tokens --query key.kid -o tsv     # → KMS_ENCRYPTION_KEY_ID

# local
openssl rand -base64 32                                       # the new KMS_LOCAL_KEY; the old one → KMS_LOCAL_PREVIOUS_KEYS
```

`KMS_ENCRYPTION_KEY_ID` is a ConfigMap value from Terraform (`config_env`), not a secret; `KMS_LOCAL_KEY` and
`KMS_LOCAL_PREVIOUS_KEYS` are secrets (§ 6 for the mechanics). Faster than the hourly job: restart the api (the first
run is 2 minutes after start), or set `KMS_REWRAP_EVERY=5m` for the day.

**Verify** — nothing left under the old key (run as the app role; an empty result per table = done):

```sql
select 'availability.calendar_links' as t, token_ref as ref, count(*) from availability.calendar_links where refresh_token_enc is not null group by 2
union all select 'catalogue.integrations', token_ref, count(*) from catalogue.integrations where credentials_enc is not null group by 2
union all select 'food.pos_connections', token_ref, count(*) from food.pos_connections where credentials_enc is not null group by 2
union all select 'booking.access_notes', key_ref, count(*) from booking.access_notes group by 2;
```

Every row shows the new reference (`local:<new fingerprint>`, the new ARN, `…/cryptoKeyVersions/<new>`, the new Key
Vault version URL); `northline_crypto_rewrapped_total{outcome="failed"}` stayed 0. Only then disable the old key
(AWS `aws kms disable-key` + `schedule-key-deletion --pending-window-in-days 30`; GCP `gcloud kms keys versions
disable <n>`; Azure `az keyvault key set-attributes --version <old> --enabled false`; local: empty
`KMS_LOCAL_PREVIOUS_KEYS`).

**Rollback.** Before the old key is disabled: point `KMS_ENCRYPTION_KEY_ID` (or `KMS_LOCAL_KEY`) back; the job re-wraps
toward the old key the same way (both stay usable). After it is disabled: re-enable it (AWS `enable-key` /
`cancel-key-deletion`, GCP `versions enable`, Azure `--enabled true`) — a disabled key is not a destroyed one; that
is why the deletion has a 30-day window.

**Comms.** Planned: ops channel. If connections were lost (old key disabled too early): support tells the businesses
to reconnect their calendar / shop / POS (Settings shows "Reconnect").

**Not possible yet:** `TOTP_KEY` (auth's authenticator secrets) and `WEBHOOK_SECRET_KEY` (the merchants' webhook
secrets) are single AES keys without a key reference per row — rotating either needs a re-encryption migration, not a
re-wrap. Treat a leak of either as an incident: for `WEBHOOK_SECRET_KEY`, every business rotates its endpoint secrets
(§ 3) after the key is replaced and the stored secrets re-created; for `TOTP_KEY`, everyone re-enrols their
authenticator. Neither has been built (open item).

## 3. Merchants' webhook signing secrets

Each partner webhook endpoint (S-33) has its own `whsec_…`, created by the api, shown once, stored encrypted. The
dual-secret window already exists: rotating keeps the previous secret in `secret_prev_enc` until `secret_prev_until`
and the worker signs every delivery with **both** (`Northline-Signature: t=…,v1=<new>,v1=<old>`), so the receiver can
switch whenever it likes inside the window ([webhooks.md § Verifying](webhooks.md#verifying-the-signature-stripes-scheme)).

**Symptoms that call for it.** The business asks (an employee with access left, a yearly policy); the secret appeared
somewhere it shouldn't (support ticket, screenshot); the receiver's logs show forged requests.

**Impact.** Planned: none during the overlap. "Stop it now" (overlap 0): deliveries fail signature checks at the
receiver until it has the new secret; Northline retries for ~3 days, so nothing is lost once it's updated.

**Decide:**

```
leaked → overlap 0 ("stop it now (it leaked)"); the receiver updates as fast as it can; failed deliveries are retried
planned → overlap 24 h (recommended) or up to 7 days for slow deploy cycles at the receiver
the receiver can't verify two v1 values? → it must accept "any v1 matches" (the documented scheme); until then use a
          short overlap and coordinate the moment
```

**Commands.** The business's owner or a member with *manage* rights: Studio › Settings › API & integrations ›
Webhooks › the endpoint › **Rotate secret** (24 h / 7 days / stop it now). API (a member's token with `acr=mfa`):

```sh
curl -X POST -H "Authorization: Bearer <member token>" -H 'Content-Type: application/json'   -d '{"overlapHours":24}' https://<api host>/api/v1/merchants/<business id>/settings/webhooks/<endpoint id>/secret
# → {"secret":"whsec_…", …}  shown once; 0–168 hours ("Keep the old secret for 0 to 168 hours." otherwise)
```

Support cannot rotate for a business (only members can — by design: the secret is shown to whoever rotates).

**Verify.** The endpoint's Deliveries drawer: deliveries after the rotation succeed; the endpoint line shows "Old
secret also signs until …"; on the receiver, the new secret verifies. After the window, only one `v1` is sent.

**Rollback.** None: the old secret can't be brought back. If the receiver needs longer than the window, rotate once
more before the window ends with a longer overlap — the receiver then switches straight to the newest secret.

**Comms.** The business tells its integrator; for a leak, support confirms with the owner that the rotation happened
and that failed deliveries will be retried.

## 4. Stripe API keys and webhook secrets

`STRIPE_SECRET_KEY` (restricted key `rk_…` preferred, [stripe.md § 2](stripe.md#2-platform-account-setup-once-per-mode)),
`STRIPE_PUBLISHABLE_KEY` (public), `STRIPE_WEBHOOK_SECRET` and `STRIPE_CONNECT_WEBHOOK_SECRET` (one per endpoint).
Test mode for dev/staging, live mode for prod — separate keys.

**Symptoms that call for it.** Yearly; a team member with Developer access leaves; a leak ([stripe-incidents.md § 5](stripe-incidents.md#5-leaked-keys)
is the emergency version of this section). A *broken* rotation: Stripe calls answer 401 (`Invalid API Key` in the
api log, checkout fails, payments job steps fail); webhooks answer 400 `invalid_signature` (Stripe › Webhooks shows
failed deliveries).

**Impact.** Planned: none inside Stripe's overlap. Wrong value deployed: checkout fails (`StripeCallFailed` 401 — not
`payments_unavailable`), jobs retry; webhooks are retried by Stripe for 3 days.

**Decide:**

```
API key: Developers › API keys › Roll key… → expiration: planned "in 24 hours" (or more) / leaked "now"
webhook secret: Developers › Webhooks › <endpoint> › Roll secret → planned: Stripe signs with both up to 24 h / leaked: expire now
publishable key: rolls with the secret key pair only if you roll the standard keys; a restricted key has none
```

**Commands.** 1) roll in the Stripe dashboard (right mode, right endpoint — there are two endpoints, two secrets);
2) put the new value in the environment's secrets manager (§ 6), e.g. AWS:

```sh
aws secretsmanager put-secret-value --secret-id northline/<env>/stripe-secret-key --secret-string 'rk_live_…'
aws secretsmanager put-secret-value --secret-id northline/<env>/stripe-webhook-secret --secret-string 'whsec_…'
```

3) force-sync the api's ExternalSecret and restart the api (§ 6); 4) verify; 5) for a planned roll, let the old key
expire on its own (or expire it early in the dashboard once verified).

**Verify.** Stripe › Developers › Logs: requests from the api with the new key (the key's last characters), all 2xx;
`kubectl -n northline-<env> logs deploy/northline-api | grep -c 'Invalid API Key'` is 0; Stripe › Webhooks › each
endpoint's latest deliveries 200; a test-mode checkout in staging succeeds.

**Rollback.** Planned: until the old key expires, put the old value back in the secrets manager and restart. After it
expired (or for a leak): roll again and deploy the new value — there is no way back to an expired key.

**Comms.** Ops channel; finance if any payout or capture was delayed.

## 5. Database, Kafka, push, OpenRouter, on-call export

Generic steps for all of them: new value at the provider → new version in the secrets manager → force-sync the
ExternalSecret → restart the apps that read it → verify → revoke the old value (§ 6 has the commands). What differs:

| secret (remote name) | apps | how to get a new value with overlap | revoke the old | impact if done wrong |
|---|---|---|---|---|
| `DB_PASSWORD` (`db-app-password`) | api, auth, worker | Terraform generates it: `terraform state list \| grep random_password` → `terraform apply -replace='<module…>.random_password.app'` writes a new value into the secret; then **at once** as the admin: `alter role northline_app password '<new>';` ([infrastructure.md § 5.1](infrastructure.md#51-postgresql-app-role-and-extensions-once-per-environment)) | — (the role has one password; open connections keep working until their pool recycles them) | between `alter role` and the restart new connections fail: do both within minutes, in a quiet hour; Flyway's migration Job uses the same secret |
| `KAFKA_SASL_JAAS_CONFIG` (`kafka-sasl-jaas-config`) | api, auth, worker | **MSK:** a second SCRAM secret / user (`aws kafka batch-associate-scram-secret`), switch the JAAS string to it. **Managed Kafka:** a new key for the service account (`gcloud iam service-accounts keys create`). **Event Hubs:** switch to the *secondary* connection string of the Send+Listen rule (`az eventhubs namespace authorization-rule keys list`) | MSK: `batch-disassociate-scram-secret`; GCP: `gcloud iam service-accounts keys delete`; Azure: `az eventhubs namespace authorization-rule keys renew --key PrimaryKey` | consumers stop (lag alerts) and the outbox backs up (`NorthlineOutboxBacklog`) until fixed; nothing is lost |
| `PUSH_APNS_KEY` + `PUSH_APNS_KEY_ID` (`push-apns-key`) | worker | Apple Developer › Keys › **+** (APNs) — two keys may exist; download the `.p8` (once!) | revoke the old key in Apple Developer after the restart | pushes to iOS fail (`unreachable` / provider paused, [push.md § 4](push.md#4-failures-and-back-off)); held pushes are retried from the deferred table |
| `PUSH_FCM_SERVICE_ACCOUNT` (`push-fcm-service-account`) | worker | Google Cloud › IAM › Service accounts › the FCM account › Keys › Add key (JSON) | delete the old key | pushes to Android fail as above |
| `OPENROUTER_API_KEY` (`openrouter-api-key`) | api | openrouter.ai › Settings › Keys › Create (same credit limit) | delete the old key | AI features answer 503 until fixed ([ai.md](ai.md#set-up-per-environment)) |
| `ONCALL_EXPORT_TOKEN` (`oncall-export-token`) | api | `openssl rand -base64 32` — **one** token, no overlap | — | the paging tool's schedule import fails (401) until its URL / header has the new token: update the paging tool right after the restart |

Not in this table: the BFF client secrets (no overlap, [secrets.md § Rotation](secrets.md#rotation)), `REDIS_PASSWORD`,
`ES_PASSWORD`, email / SMS keys (same table there), `TOTP_KEY` and `WEBHOOK_SECRET_KEY` (§ 2 — not rotatable yet).

**Verify** per secret: the apps restarted cleanly (`kubectl rollout status`), and — DB: `select usename, count(*) from
pg_stat_activity where datname = 'northline' group by 1` shows the apps connected; Kafka: `northline_events_consumed_total`
rising, `northline_events_outbox_pending` low; APNs/FCM: `northline_notifications_sent_total{channel="push",outcome="sent"}`
rising; OpenRouter: an AI action in the Studio works; on-call: `curl -s -o /dev/null -w '%{http_code}' -H
"Authorization: Bearer <new token>" https://<api host>/api/v1/ops/oncall` → 200 and the paging tool's import succeeds.

**Rollback.** Until the old value is revoked: put it back in the secrets manager, force-sync, restart. That's why the
revoke is always the last step.

**Comms.** Ops channel. On-call: tell whoever owns the paging tool. A DB password rotation: announce the quiet-hour
window.

## 6. External Secrets commands per cloud

Remote names: AWS `northline/<env>/<name>`, Google Cloud `northline-<env>-<name>`, Azure Key Vault `<name>`
([secrets.md](secrets.md#how-it-fits-together)). Never paste a secret on the command line in a shared shell history:
read it from a file or a prompt (`read -rs VALUE`).

```sh
# 1. a new version of the secret
read -rs VALUE
aws secretsmanager put-secret-value --secret-id northline/<env>/<name> --secret-string "$VALUE"
printf %s "$VALUE" | gcloud secrets versions add northline-<env>-<name> --data-file=- --project <project>
az keyvault secret set --vault-name <nl-<env>-sec-…> --name <name> --value "$VALUE" --output none
#    a file (APNs .p8, FCM JSON):  --secret-string file://AuthKey.p8 · --data-file=AuthKey.p8 · --file AuthKey.p8

# 2. refresh the Kubernetes Secret now instead of within the hour (externalSecrets.refreshInterval)
kubectl -n northline-<env> annotate externalsecret northline-<app> force-sync=$(date +%s) --overwrite
kubectl -n northline-<env> get externalsecret northline-<app> -o jsonpath='{.status.conditions[0].reason}{"\n"}'   # SecretSynced

# 3. restart what reads it (pods read their environment at start)
kubectl -n northline-<env> rollout restart deploy/northline-<app>
kubectl -n northline-<env> rollout status deploy/northline-<app> --timeout=5m

# 4. revoke the old value at the provider; then disable the old version in the secrets manager (optional, tidy)
aws secretsmanager list-secret-version-ids --secret-id northline/<env>/<name>          # AWSPREVIOUS is the old one
gcloud secrets versions disable <old version> --secret northline-<env>-<name> --project <project>
az keyvault secret set-attributes --vault-name <…> --name <name> --version <old version> --enabled false
```

`<app>` is `api`, `auth`, `bff`, `consumer-bff`, `console-bff` or `worker` ([secrets.md § Secret inventory](secrets.md#secret-inventory)
says which app reads which variable); a secret read by several apps → repeat 2 and 3 for each. Argo CD (S-15) doesn't
fight the restart (it only changes a pod-template annotation it doesn't manage). Rolling back a value = step 1 with
the old value (AWS keeps it as `AWSPREVIOUS`; Google Cloud and Key Vault keep every version), then 2 and 3.

**Exercised:** on kind with ESO's `fake` provider in S-6 (steps 2–3); the cloud CLIs in step 1 and 4 have **not** run
against a real account.
