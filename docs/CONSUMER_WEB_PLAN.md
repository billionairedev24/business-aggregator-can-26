# Consumer web plan (`web/apps/consumer`, design 06)

Scope: everything in `design/06 Consumer Web.dc.html` — the screens and states listed in `docs/SCREENS.md` § Consumer
web — built story by story (E-7: S-45 … S-63). S-45 laid the foundation described here; every later story builds one
or more screens on top of it without touching another story's routes. This file is the consumer counterpart of
`docs/IMPLEMENTATION_PLAN.md` (the Studio's), whose frontend and backend conventions still apply unless this file says
otherwise. Source-of-truth order: `CLAUDE.md`.

## Decisions that shape everything

- **TanStack Start with server-side rendering** (not an SPA like the Studio). Provider, product, restaurant and category
  pages must be indexable (S-63: SEO, sitemap, structured data) and fast on phones. Start renders every route on the
  server and hydrates it; navigation after that is client-side. Node server: `server/node-server.mjs` (port 3000,
  `/healthz`), image `web/Dockerfile` target `consumer`.
- **Server-rendered pages are the same for everyone.** The server fetches only public data, as a guest, through the
  consumer-bff (`NL_BFF_URL`, in-cluster). Who is signed in, the cart, the account menu's values and the location are
  loaded in the browser after hydration. So pages can be cached at the edge later, and the SSR server never holds a
  session. (A screen that is only meaningful signed in — orders, account — renders its skeleton on the server.)
- **consumer-bff = the bff jar with the `consumer` Spring profile** (`server/bff/src/main/resources/application-consumer.yml`),
  deployed as its own Deployment `northline-consumer-bff` (port 8081). One codebase keeps CSRF, cookies, the S-19
  revocation check and the S-20 hardening identical for both BFFs; the profile changes the OAuth client
  (`consumer-bff`), the cookie (`__Host-NL_CONSUMER`) and lets **guests** browse. Runbook:
  `docs/runbooks/README.md` § Consumer BFF.
- **Consumers don't need a second factor.** `acr=mfa` appears only when a passkey or authenticator was used; the api
  requires it for merchant and staff endpoints only. Consumer endpoints must not require it (payments may ask for a
  step-up later — S-51 decides).

## Frontend conventions (in addition to IMPLEMENTATION_PLAN.md § Frontend conventions)

- **Server-safe code.** No `window`/`document`/`localStorage` at module scope or during render; read them in effects
  (or `createIsomorphicFn` like `lib/request.ts`). The first client render must equal the server's (hydration): start
  from a neutral state ("Locating…", a skeleton) and update in an effect.
- **Data loading.** `features/<f>/api.ts` exports `queryOptions` factories. Public, SEO-relevant data: the route's
  `loader` calls `context.queryClient.ensureQueryData(xQuery(params))` and the screen `useSuspenseQuery(xQuery(params))`
  — the server fetches, dehydrates, the browser hydrates without refetching. Personal data (session, cart, orders):
  `useQuery` in the component only (not in loaders), so it is fetched in the browser. Loaders throw `notFound()` for a
  404 so the not-found screen renders.
- **HTTP.** `http()` from `@northline/client` (same-origin through the BFF; CSRF header on non-GET; 422 →
  `ValidationError` → `serverFieldErrors`; `Idempotency-Key` for money-moving POSTs). Never call the api host
  directly. On the server `http()` prefixes `NL_BFF_URL` (set in `router.tsx`).
- **Links.** Inside routes use TanStack `<Link>`; kit components render `SiteLink`, which the root routes through the
  router (`RouterSiteLink`: plain left clicks navigate client-side; new tabs, modifiers and `*.html` files don't).
- **i18n.** `defineMessages({ en, fr })` per feature, fr-CA wording from `design/i18n-fr.js`. The language comes from
  the `nl.locale` cookie (the header/footer toggle writes it), else `Accept-Language`; the server renders in it and
  sets `<html lang>`. Money/dates: `useFormatters()` (America/Edmonton).
- **Titles.** Each route sets `head: ({ match }) => ({ meta: [{ title: … }] })` in the request's language
  (`match.context.locale`); `pageTitle(locale, screenKey)` gives "Cart · Northline". SEO pages (S-63) add description,
  canonical, `hreflang` and JSON-LD there.
- **CSS.** Tokens only, `nl-` prefix. A feature's stylesheet is linked from its route's `head().links` with a `?url`
  import (`import css from '../features/cart/cart.css?url'` → `{ rel: 'stylesheet', href: css }`) so the server's HTML
  carries it before first paint — as `__root.tsx` does for tokens, the kit and the shell. Unlike the Studio, the
  consumer app keeps `--color-surface` as the tokens define it (design 06: surfaces on the off-white page).
- **States** (docs/SCREENS.md § Every screen must implement): skeleton while loading (`pendingComponent` or a
  Suspense fallback shaped like the screen), empty (one line + primary action, `EmptyState`), error (`ErrorState` with
  Retry inside the page; anything escaping lands on the route's `RouteError`, whose Retry resets queries and re-runs
  loaders). No horizontal scroll ≥ 320 px, 44 px targets, focus ring, `lang` on mixed-language text.
- **Guests.** Every screen works signed out as far as the design allows; screens flagged `guestBanner` in
  `features/shell/screens.ts` get the "You're browsing as a guest…" banner from the shell (cart, book, food checkout,
  orders, account, quote). Actions that need an account link to `signInHref(currentHref)`; never redirect a guest away
  from a page they can read.
- **Tests.** vitest + Testing Library + jest-dom; `renderApp(path, { locale, geolocation })` renders the shell and
  every route; `mockFetch(handler)` stubs the BFF/api. Cover en and fr-CA copy, the states, validation messages and
  the main interactions. UI-kit pieces: a story per state (a11y addon must pass).

## Contracts

### Session (consumer-bff)

- `GET /bff/session` → always `200 { user: {id, firstName, lastName, email, phone, initials, locale, memberSince} | null,
  acr?, sid?, guestId, location?: { city } }`. `user: null` = a guest. `guestId` = the browsing session's id (see Cart).
  `location.city` = the CDN's guess from the IP (only when `CLIENT_CITY_HEADER` is configured).
  Client: `sessionQuery` / `useViewer()` in `features/session/api.ts` (browser only).
- `GET /bff/login?next=/path` → the sign-in hand-off (authorization code + PKCE with client `consumer-bff`); lands on
  `next` (local paths only). The sign-in pages (S-62) call it after the auth JSON API signed the person in: a
  sign-in lands back on `next`, a new account on `/location`. A person may be signed in with a phone code only (no
  `acr`); screens that need more (saved cards, S-51) ask for a step-up there.
- `POST /bff/logout` → 204 (CSRF header). `useSignOut(authOrigin)` also ends northline-auth's session.
- CSRF: cookie `__Host-XSRF-TOKEN` (`XSRF-TOKEN` locally), header `X-XSRF-TOKEN` only — for guests' POSTs too.
- `signInHref(next, 'sign-in' | 'register')` builds `/sign-in?next=…`.

### Guest id and cart (S-51 owns the cart)

- The consumer-bff relays `X-Northline-Guest: <guestId>` on every `/api` call of a browsing session (signed in or
  not) and drops any the browser sends. It is a random 128-bit key, not an identity.
- `GET /api/v1/cart` → `{ itemCount, … }` — the cart of the signed-in person, else of the guest id. Guests must be
  allowed (open the path in the api's `SecurityConfig` and key it by the header). The header reads `itemCount`
  (`cartQuery`, key `['cart']`); every cart mutation invalidates it. On sign-in the api merges the guest's cart into the
  person's (the guest id arrives with the first signed-in call). Until the endpoint exists the header shows 0.

### Location

`useDeliveryLocation()` (`features/location`) → `{ location: { status, label, city, lat?, lng?, source, province?, street?,
unit?, postalCode?, placeId?, marketId?, zoneId?, zone? }, save, forget }`.
Order: saved (`localStorage['nl.location']`, written by `save({ label, city, lat?, lng?, placeId?, street?, unit?,
province?, postalCode?, marketId?, zoneId?, zone? })` on the Location screen — S-47 added everything after `placeId`,
all optional) → the device's geolocation, named by `GET /api/v1/geo/reverse?lat&lng → { label, city, province?,
market?: {id, city, province, stage}, zone?: {id, name, …} }` (S-47; 404 when nothing is known there; a `market` that is
null or not live/pilot counts as outside every market), else the nearest live market (Calgary, Edmonton, Airdrie within
40 km) → the IP city → Calgary. Statuses map to the pill's copy: `locating`, `detected` ("Detected · deliver to"),
`fallback` / `saved` ("Deliver to"). Screens filter by `location.city` (and `lat/lng` when present); checkout reads the
saved address parts (`street`, `unit`, `postalCode`, `province` — the province is the place of supply for tax, S-21).
Server-side the location is unknown: render location-independent content or a skeleton. `/location?next=/path` comes
back to `next` after Save (checkout's "Change").

**Geo api (S-47, public under `/api/v1/geo`, the Google key on the server):** `GET /markets` (provinces → markets with
stages), `GET /autocomplete?q=&session=&lat=&lng=` (Canada only; ≥ 3 characters; one `session` token per address
search), `GET /places/{placeId}?session=` (the address + `resolution: { market, zone, waitlist }`), `GET /reverse`,
`GET /resolve?lat=&lng=`, `POST /waitlist { regionId, email? }` (guests give an email; 201, or 200 when already on it).
Lookups are limited per browsing session (429 `rate_limited`); Google failures are 503 `places_unavailable`.

### Account menu

Items and routes in `features/shell/AccountArea.tsx` (`ACCOUNT_LINKS`). Values come from
`GET /api/v1/me/account-summary` → `{ reliability?, points?: {balance, valueCents}, plus?, activeOrders?, favourites?,
openCases?, paymentMethod?: {brand, last4}, addresses?: {count, members}, signIn?: passkey|totp|sms, quietHours?:
{from, to}, dietary?: string[], province? }` (every field optional; S-58/S-59 provide it). Mutations that change a
value invalidate `accountSummaryQuery`.

### Language

Cookie `nl.locale` = `en` | `fr` (1 year, not HttpOnly). `useLocale().setLocale()` switches in place and writes it.

accept single-factor tokens. Anything a guest may do (cart) must read `X-Northline-Guest`.
