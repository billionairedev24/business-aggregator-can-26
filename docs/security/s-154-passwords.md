# S-154 — email + password accounts: security notes

Scope: northline-auth's create account, email verification, password sign-in, enrolment of the first second factor,
forgot / change password (2026-10-20). Code: `server/auth` (`AccountService`, `SignInService.startWithPassword`,
`EnrollmentService`, `PasswordService`, `EmailCodeGate`, `PasswordPolicy`, `config/PasswordHashing`); tests:
`AccountSignUpApiTest`, `MailpitAccountEmailTest`, `PasswordPolicyTest`, `PasswordHashingTest`.

| concern | what northline-auth does |
|---|---|
| Hashing | Argon2id (Spring Security's `Argon2PasswordEncoder` on BouncyCastle), salt 16 B, hash 32 B, m = 19 MiB, t = 2, p = 1 (`PASSWORD_HASH_*`), stored as `{argon2}$argon2id$…` in `auth.passwords` (one row per account, outside `identity.users` so no api query can select it). The password is NFKC-normalised before hashing and comparing. Not a `PasswordEncoder` bean (the authorization server would use it for client secrets). |
| Policy (NIST SP 800-63B § 3.1.1) | 12–128 characters (code points), any characters, no composition rules, not one of ~1,200 common / breached passwords of 12+ characters (`auth/common-passwords.txt`, from the NCSC top-100k via SecLists), not the email or its local part, not one repeated character. The same rules client-side except the list. |
| Never logged | The password is a request field only: no log line, audit row or event carries it (audit rows hold ids, the app, the factor). Logs mask addresses (`DefaultMailer.masked`). |
| Enumeration | Create account answers `202 verify-email` for every address: an address with an account gets an "account exists" email instead of a code, and every code typed for it is "wrong". Sign-in: the same 422 (`password` `mismatch`, "That email and password don't match…") for an unknown email, an account without a password and a wrong password, after the same Argon2 work (a decoy hash). Forgot password answers the same for an unknown address and sends nothing. Emails go out after commit on another thread, so response time doesn't show whether one was sent. |
| Email codes | 6 digits + a 256-bit link token per email; only SHA-256 hashes stored (`auth.email_codes`), constant-time comparison, 15 min, single use (conditional update), 5 wrong tries lock the code, a new email retires the old code, 60 s resend cool-down. A link confirms an address from any browser but signs in only the browser that sent the form — elsewhere the password is asked, so an intercepted link alone can't enrol a factor. |
| Pending accounts | Unconfirmed accounts live in `auth.pending_accounts`, never in `identity.users`; registering the same address again replaces the pending row (no squatting an address one can't read); forgotten after 7 days. The optional mobile is stored unverified and is never used for phone sign-in codes until confirmed by SMS (S-62); a later SMS-verified registration takes the number over. |
| Rate limits / lockout | S-9 limiter (Valkey; memory under local/test), per account, IP and session, progressive (lockout × 2^(n-1)): `password-verify` 10 / 15 min per account, 30 per IP; `email-send` 5 / h per address, 20 per IP; `email-code-verify` 10 / h per account, 50 per IP. All three are guessable-secret paths: they fail closed in staging/prod when Valkey is down (S-20). Lockouts are audited (`auth.rate_limited`). |
| Second factor | The password alone never gives `acr=mfa`; Studio, console and MCP clients still refuse such sessions (MfaRequiredClients). An account without a passkey or authenticator is sent to enrolment (`/api/auth/enroll/*`) — allowed only while it has none (409 `already_enrolled` otherwise), so a stolen password can't add a factor to a protected account. Identifier-first sign-in can't skip a password the account has: its TOTP / backup code counts only after the password (passkeys may still come first). |
| Sessions | The session id changes at sign-in, at enrolment and at step-up. A password reset ends every session of the account (refresh tokens deleted); a password change ends every other session. Changing the password, the authenticator or the backup codes needs a second factor from the last 10 minutes (step-up) and counts against `security-change`. |
| CSRF | Unchanged JSON-API rules (S-20): Origin allow-list on every state-changing `/api/auth/**` request, JSON bodies only, CORS for the three apps. |
| Audit | `developer.audit_log`: `auth.account_created`, `auth.factor_enrolled`, `auth.password_reset`, `auth.password_changed` / `auth.password_set`, `auth.authenticator_added` / `_replaced`, `auth.backup_codes_regenerated`, `auth.session_revoked` (reason `password_reset` / `password_changed`); payloads hold no email, phone or password. `user.registered` (ids only) when the email is confirmed. |
| Erasure | `auth.passwords` and the account's `auth.email_codes` are purged with the other auth rows (S-105). |

Open items: no breached-password API lookup (k-anonymity, e.g. HIBP) — the bundled list only; no notification email on a
password change; the mobile apps' native screens still use the phone-code flows (they can't sign in with a password yet).
